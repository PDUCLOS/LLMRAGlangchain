Un copilote ERP qui cite ses sources et refuse d'inventer.

Un DAF pose une question en français. Le copilote cherche dans les procédures internes et interroge l'ERP en lecture seule. Il répond avec la source de chaque affirmation et refuse quand il ne sait pas. Il tourne sur un GPU de bureau, sans qu'aucune donnée ne sorte du poste, et chaque changement est mesuré avant d'être livré.

Le problème

Dans un ERP, une réponse plausible mais fausse coûte cher

Ce que demandent les équipes finance

  • « Un client a 70 jours de retard : garde-t-il sa remise ? »
  • « Quelles factures dépassent 60 jours de retard ? »
  • « Quelles sont les étapes de la clôture mensuelle ? »

La réponse est à moitié dans les documents (procédures, contrats) et à moitié dans les données de gestion.

Ce qu'un chatbot générique fait de travers

  • Il invente un chiffre ou un numéro de facture qui « sonne juste ».
  • Il ne dit pas d'où vient l'information.
  • Il envoie des données clients à un service externe.
  • Personne ne sait s'il s'est dégradé après une mise à jour.

Ce que fait ce copilote

  • Ancrage : chaque phrase porte sa source [S1], sinon il refuse.
  • Chiffres exacts : les montants viennent d'une requête SQL en lecture seule, jamais du modèle.
  • Confidentialité : LLM open-weight sur le GPU de l'entreprise.
  • Mesure : un banc LLMOps note chaque version avant livraison.
Démo réelle

Captures prises sur la machine de démonstration

Les captures ne sont pas des maquettes. Elles viennent de l'API lancée sur un Ryzen 9 avec une RTX 4070 Ti SUPER, avec gemma4:e4b servi par Ollama et la chaîne LangChain. Le pied de chaque réponse affiche le modèle, les tokens, la latence et le coût équivalent Azure.

Comment ça marche

Le trajet d'une question, en six étapes

Chaque étape est décrite en clair, avec le fichier qui la contient et la raison du choix. Le cœur applicatif tient en moins de 4 000 lignes de Python commentées en français.

Découper les documents

En clair
Les procédures et contrats sont coupés en fragments d'environ 800 caractères, en respectant les titres de section.
Code
rag/chunking.py · erp-ai ingest
Pourquoi
Un fragment = une idée. On peut alors citer « Politique commerciale § 3 » au lieu d'un document de 20 pages.

Transformer le texte en vecteurs

En clair
Chaque fragment devient une liste de 1 024 nombres (un embedding). Deux textes de même sens ont des vecteurs proches, même avec des mots différents.
Code
providers/embeddings.py — modèle bge-m3 via Ollama
Pourquoi
bge-m3 est multilingue et bon en français. Il tourne sur le GPU local.

Chercher de deux façons, puis fusionner

En clair
On cherche par mots-clés (BM25) et par sens (vecteurs), puis on combine les deux classements (fusion RRF).
Code
rag/retrieval.py
Pourquoi
Les mots-clés trouvent « F-2026-0007 » ou « TVA ». Les vecteurs trouvent « délai de paiement » quand on demande « échéance ». Ensemble, le bon document figure toujours dans les 5 premiers résultats, et presque toujours en tête (MRR 0,92 sur 1).

Interroger l'ERP, en lecture seule

En clair
Si la question porte sur des données (impayés, chiffre d'affaires), le copilote lance une requête SQL encadrée. Les jours de retard sont calculés en Python.
Code
agents/tools.py · agents/safe_sql.py
Pourquoi
Un LLM calcule mal. Deux verrous indépendants : validate_readonly_sql() (une seule instruction, tables autorisées) et un compte SQL qui n'a que le droit SELECT.

Générer une réponse ancrée

En clair
Le modèle reçoit les sources numérotées et une consigne stricte : citer chaque affirmation, refuser si rien ne couvre la question.
Code
rag/prompts.py · rag/langchain_chain.py (LCEL + ChatOllama)
Pourquoi
Deux chaînes, native et LangChain, avec les mêmes sources et les mêmes citations. Si LangChain tombe, la chaîne native prend le relais : une panne de bibliothèque ne coupe pas le service.

Tout journaliser

En clair
Chaque appel enregistre le rôle de l'utilisateur, le modèle, les tokens réellement consommés, le coût, la latence et les sources citées.
Code
observability/usage.py · GET /usage
Pourquoi
C'est la base du pilotage : coût par client, dérive de latence, taux de refus. On peut le brancher sur Power BI.
Architecture

Un seul code, trois environnements

Le même code tourne en CI (providers déterministes, sans réseau), sur un poste GPU (Ollama) et sur Azure (Azure OpenAI, AI Search). On bascule par variables d'environnement, sans modifier le code. Les schémas viennent de docs/architecture.drawio, qui s'ouvre dans draw.io.

LLMOps

Mesurer, détecter, corriger, vérifier

Un modèle de langage ne plante pas, il se trompe poliment. Pour savoir s'il se trompe, il faut un banc de mesure. Ici, 13 questions (10 questions métier, 2 hors sujet, 1 injection de prompt) sont posées à 4 configurations. Chaque réponse est notée par deux LLM juges de familles différentes.

1 · Mesurer

Premier banc

qwen3.5 obtient 4,8 / 5 de fidélité, gemma4 4,85 / 5. Le mode extractif d'origine plafonne à 3,1 / 5.

2 · Détecter

Le juge trouve une invention

Sur « retards de plus de 60 jours », qwen cite 3 numéros de facture qui n'existent pas. La métrique « citations valides » ne l'avait pas vu.

3 · Corriger

La cause est dans l'outil, pas dans le modèle

L'outil SQL renvoyait tous les impayés sans ancienneté. Il calcule maintenant les jours de retard et filtre sur le seuil demandé.

4 · Vérifier

Nouveau banc : 5 / 5 partout

Les deux juges donnent 5 / 5 à tous les modèles Ollama. Aucune facture inventée.

Démarche

Le journal de la mise en route

Ce qui a été fait, dans l'ordre, y compris ce qui n'a pas marché du premier coup.

Analyse

Inventaire de la machine

Ryzen 9 3900X, 32 Go, RTX 4070 Ti SUPER 16 Go, Python 3.12, Docker, Ollama déjà installé avec deux modèles. Le GPU permet de servir un vrai LLM en local.

Référence

Faire tourner le projet tel quel

66 tests verts, gold set à 100 %. Mais le « LLM » local n'en était pas un : il recopiait des phrases. Il fallait une vraie démo.

Fonctionnalité

Provider Ollama

LLM_PROVIDER=ollama et EMBEDDING_PROVIDER=ollama, plus ChatOllama dans la chaîne LangChain. Le service enregistre désormais les tokens réellement mesurés par le modèle, et non plus une estimation.

Mesure

Banc LLMOps

4 configurations, 13 questions, 2 juges, latence p50 / p95, coût. Le banc produit un rapport JSON et un tableau de bord HTML.

Correctif · banc

Le juge ne voyait pas tout

Première version : le juge ne recevait que les documents, pas les lignes SQL. Il notait 1 / 5 une réponse juste. Corrigé : le juge voit exactement ce qu'a vu le modèle.

Correctif · CI

La CI de main était rouge

Un vrai SQL Server 2022 (Docker) a révélé quatre défauts que SQLite masquait : séparateurs GO absents, schéma non ré-exécutable, fonction date() inexistante en T-SQL, deux tests non portables. Résultat : 76 / 76 tests sur SQL Server.

Correctif · qualité

Hallucination corrigée à la source

L'outil SQL calcule désormais l'ancienneté des impayés. Les juges passent de 4,8 à 5 / 5.

Livraison

Interface, conteneur, Kubernetes

Interface de chat sur /. Image Docker testée de bout en bout : un conteneur d'ingestion crée la base et indexe, un conteneur API répond, avec SQL Server et Ollama. Manifestes Kubernetes validés par kubectl kustomize.

Kubernetes

Mettre la solution sur un cluster

Tout est dans deploy/k8s : une base commune et deux variantes (overlays), l'une pour un cluster GPU local, l'autre pour le cloud (AKS). Une seule image sert l'API, le Job d'ingestion et le banc LLMOps : seule la commande change.

Les pièces, et pourquoi chacune

RessourceRôle
Deployment erp-ai-api + HPAL'API est sans état : on la réplique (2 à 6 pods selon le CPU). Sondes sur /health, utilisateur non root.
Deployment ollamaLe LLM, sur un nœud GPU (nvidia.com/gpu: 1). Une seule réplique par GPU, stratégie Recreate.
StatefulSet mssqlSQL Server avec un volume stable. Il est remplacé par Azure SQL dans l'overlay cloud.
Job erp-ai-ingestApplique le schéma sur une base vide, crée les comptes à moindre privilège (sql/01_roles.sql), charge les données, indexe les documents. Ré-exécutable : les données existantes sont conservées.
CronJob llmops-benchLe banc LLMOps chaque nuit, sur une base jetable : il détecte une dérive après un changement de modèle.
PVC erp-ai-dataL'index vectoriel, écrit par le Job et lu par l'API. Il doit être en ReadWriteMany dès qu'il y a plusieurs répliques.
ConfigMap / SecretLes mêmes variables que le fichier .env. Changer de modèle = changer une ligne. L'API se connecte avec le compte erp_app (pas de DDL) ; le compte admin n'est donné qu'au Job d'initialisation.
NetworkPolicySQL Server et Ollama ne sont joignables que depuis les pods de l'application.

Déployer sur un cluster GPU local

Docker Desktop (Kubernetes activé), k3s ou minikube, sur une machine NVIDIA avec le device plugin installé.

# 1. Construire l'image (une seule pour API, Jobs, banc)
docker build -t erp-ai-copilot:0.2.0 .

# 2. Vérifier ce qui sera créé, puis l'appliquer
kubectl kustomize deploy/k8s/overlays/local-gpu
kubectl apply -k deploy/k8s/overlays/local-gpu

# 3. Suivre les Jobs : modèles téléchargés, base indexée
kubectl -n erp-ai wait --for=condition=complete job/ollama-pull-models --timeout=30m
kubectl -n erp-ai wait --for=condition=complete job/erp-ai-ingest --timeout=10m

# 4. Ouvrir l'interface
kubectl -n erp-ai port-forward svc/erp-ai-api 8000:80
#    puis http://localhost:8000

# Réindexer après un changement de corpus
kubectl -n erp-ai create job reindex --from=job/erp-ai-ingest

Passer au cloud (AKS)

az acr build -r monregistre -t erp-ai-copilot:0.2.0 .
kubectl -n erp-ai create secret generic erp-ai-secrets \
  --from-literal=DATABASE_URL="mssql+pyodbc://...azure..." \
  --from-literal=MSSQL_SA_PASSWORD="inutilisé-en-cloud"
kubectl apply -k deploy/k8s/overlays/cloud

Points d'attention

Le GPU est le goulot. Ajouter des pods d'API n'accélère pas la génération. Pour monter en charge, on ajoute des nœuds GPU (une réplique d'Ollama par GPU) ou on bascule sur Azure OpenAI.

Pas de SQLite en cluster. Plusieurs pods ne peuvent pas écrire le même fichier. On utilise SQL Server ou Azure SQL.

Index vectoriel. Le fichier local suffit avec un volume partagé. Au-delà, VECTOR_STORE_PROVIDER=azure_ai_search.

Secrets. secret.yaml contient des valeurs à changer. En production, on utilise Key Vault ou External Secrets.

Authentification. L'overlay cloud place oauth2-proxy (Entra ID) devant l'Ingress. Étape suivante : déduire le rôle (DAF, contrôleur…) des groupes Entra ID au lieu de le lire dans la requête. L'émulateur d'API ERP n'est exposé qu'en développement.

Ce qui a été vérifié

L'image a été construite, puis exécutée comme dans le cluster : conteneur d'ingestion vers SQL Server et Ollama, puis conteneur API avec index en lecture seule, utilisateur 10001 et healthcheck au vert. Réponse sourcée en 2,3 s.

Les deux overlays sont rendus sans erreur par kubectl kustomize : 17 ressources en local GPU, 14 en cloud.

Pas encore fait : un kubectl apply sur un cluster réel, et le passage du Job avec séparation des comptes (admin / erp_app) en conteneur, interrompu par la saturation mémoire de la VM Docker. C'est la première étape de la feuille de route.

Glossaire

Les mots du projet

RAG
Retrieval-Augmented Generation : on cherche d'abord les bons passages, puis on demande au modèle de répondre uniquement à partir d'eux.
Embedding
Représentation d'un texte par un vecteur de nombres. Des textes de sens proche donnent des vecteurs proches.
BM25
Score classique de recherche par mots-clés, celui des moteurs de recherche. Il est précis sur les codes et les termes exacts.
RRF
Reciprocal Rank Fusion : on additionne 1 / (60 + rang) de chaque classement. C'est simple et robuste.
LLM juge
Un second modèle note la réponse du premier, ici sur la fidélité aux sources, de 1 à 5. On en utilise deux pour lisser leurs biais.
p50 / p95
Latence médiane, et latence que 5 % des requêtes dépassent. Le p95 est ce que l'utilisateur ressent les mauvais jours.
LCEL
LangChain Expression Language : une chaîne écrite comme un tuyau, prompt | modèle | extraction.
Ollama
Serveur qui fait tourner des modèles open-weight (gemma, qwen) sur le GPU, avec une API HTTP simple.
HPA
Horizontal Pod Autoscaler : Kubernetes ajoute ou retire des pods selon la charge.
PVC
Persistent Volume Claim : une demande de disque qui survit au redémarrage des pods.
StatefulSet
Variante du Deployment pour les applications avec état (bases de données) : identité et disque stables.
kustomize
Outil intégré à kubectl : une base de manifestes, et des overlays qui la modifient par environnement.
